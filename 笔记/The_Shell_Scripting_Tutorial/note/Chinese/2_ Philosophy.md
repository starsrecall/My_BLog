# 设计理念
Shell脚本编程在部分Unix系统管理员群体中口碑不佳，通常源于两个原因：
*   作为解释型程序，Shell脚本的运行速度远低于C程序，甚至比同为解释型的Perl程序也要慢。
*   编写简单批处理类Shell脚本的门槛极低，导致市面上充斥着大量质量低劣的Shell脚本。

正因如此，写出**优质**Shell脚本也成了一件颇有技术成就感的事。比如写得好的Shell脚本甚至可以用作CGI程序，速度不会比Perl落后太多（当然如果只看速度，两者在大多数场景下都不如C程序）。

要写出清晰、简洁、高效的Shell脚本，需要遵循几个核心原则：
*   最重要的标准是排版清晰可读
*   第二是避免使用不必要的命令

排版清晰与否，直接决定了一个Shell脚本是没人能懂的“黑魔法”，还是易于维护、逻辑易懂的工具。你可能会觉得简单脚本不需要太在意排版，但有两点值得牢记：
1.  第一，简单脚本发展成复杂大脚本的频率，远比你预想的要高。
2.  第二，如果其他人都看不懂你的脚本逻辑，你就得一辈子自己扛下维护它的苦活！

Shell脚本似乎天生就容易出现缩进混乱的问题，而Shell的主要控制结构都是`if/then/else`和各类循环，因此缩进对理解脚本逻辑至关重要。

很多Shell脚本的典型缺陷是写这类冗余代码：
```bash
cat /tmp/myfile | grep "mystring"
```
而它的等效写法性能要高得多：
```bash
grep "mystring" /tmp/myfile
```

你可能觉得这点开销不值一提：操作系统需要加载`/bin/grep`可执行文件（我本机上这个文件只有75600字节，体积很小），在内存中创建用于数据传输的**管道（Pipe）**，再加载并运行更小的`/bin/cat`（我本机仅9528字节），把`cat`的输出挂载到管道的输入端，再执行整个流程。

当然这类操作本就是操作系统的本职工作，通常执行效率很高。但如果这段命令是放在循环中重复执行，省去查找加载`cat`程序、创建销毁管道的开销，带来的性能提升就会相当可观——尤其是在CGI这类环境中，本身影响响应速度的其他因素已经很多，脚本本身就不要再额外拖后腿了。不同Unix发行版在“进程创建与销毁”（即加载程序、执行、清理资源的完整流程）的效率上存在差异，但不管你用的Unix系统性能有多强，能少做的操作永远比多做好。

因此你可能听说过「无用cat使用奖（Useless Use of Cat Award, 简称UUoC）」，有些圈子也叫它**“严肃Shell脚本中最毫无必要使用cat大奖”**，这个奖项时不时就会在`comp.unix.shell`新闻组里被大家拿出来调侃。这本质上是同行互相监督、共同规范代码写法的一种趣味方式，确保大家都用最佳实践写脚本。

这也正好引出另一个原则：永远不要对自己写的Shell脚本敝帚自珍。Shell脚本天生就无法闭源，如果你给客户提供了Shell脚本，对方可以很轻松地读取源码。所以不如坦然接受脚本会被所有使用者审阅的事实，甚至可以用[GPL（GNU通用公共许可证）](http://www.gnu.org/copyleft/gpl.html)开源你的脚本，鼓励大家免费给你反馈问题、修复bug！

【背景补充说明】
UUoC（无用cat使用奖）是Unix技术圈最知名的梗之一，最早起源于1990年代的`comp.unix.shell`新闻组，至今仍被广泛用来调侃冗余的`cat`用法。除了文中提到的`cat 文件 | grep`反例，常见的冗余cat写法还有`cat 文件 | wc -l`（可替换为`wc -l 文件`）、`cat 文件 | sort`（可替换为`sort 文件`）等，避免这类冗余不仅能减少系统开销、提升脚本性能，也能让代码逻辑更简洁易懂。
