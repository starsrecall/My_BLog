# 信用卡校验（Credit）

![手持信用卡的人](./credit_English.assets/credit_cards.jpeg)
## 待解决问题
信用卡（或借记卡）是用于购买商品与服务的支付卡片，卡面上印有一串卡号，该卡号同时存储在对应机构的数据库中，因此当你刷卡消费时，发卡机构就能知晓该向谁推送账单。全球信用卡用户数量极多，因此卡号长度通常很长：美国运通（American Express）卡号为15位，万事达卡（MasterCard）为16位，维萨卡（Visa）为13位或16位。且卡号为十进制数（0-9）而非二进制数，这意味着理论上美国运通最多可以发行10^15 = 1,000,000,000,000,000张不重复的卡片，也就是1千万亿张。
实际上这个数字存在高估，因为信用卡号本身有固定结构：所有美国运通卡号以34或37开头；多数万事达卡号以51、52、53、54或55开头（本题不涉及其他可能的开头规则）；所有维萨卡号以4开头。此外信用卡号还内置了**校验和（checksum）**，即卡号各位数字之间存在特定数学关联。这种校验和机制让计算机（或是喜欢数学的人）无需查询速度较慢的数据库，就能检测出输入错误（比如数字换位），甚至可以识别部分伪造卡号。当然，不怀好意的专业人员完全可以构造出符合该数学规则的假卡号，因此更严格的校验仍需要查询数据库。

请在名为`credit`的文件夹中创建`credit.c`文件，用C语言实现一个程序，校验给定信用卡号的合法性。

## 卢恩算法（Luhn's Algorithm）
信用卡号的校验规则是什么？大多数信用卡采用IBM工程师汉斯·彼得·卢恩发明的算法，按照**卢恩算法**，你可以通过以下步骤判断信用卡号是否（格式层面）合法：
1. 从卡号的倒数第二位开始，每隔一位取出数字乘以2，再将所有乘积的每一位数字相加（而非直接相加乘积本身）。
2. 将上述结果与未乘以2的各位数字的总和相加。
3. 如果最终总和的最后一位是0（更正式的表述是：总和**模运算（modulo）**10等于0），则该卡号合法！
这个规则可能有点抽象，我们用大卫的维萨卡（卡号4003600000000014）举个例子：
1. 为了便于说明，我们先从倒数第二位开始，给每隔一位的数字加上下划线：
    4̲003̲6̲000̲000̲001̲4
    现在把这些加下划线的数字分别乘以2：
    1•2 + 0•2 + 0•2 + 0•2 + 0•2 + 6•2 + 0•2 + 4•2
    得到的乘积为：
    2 + 0 + 0 + 0 + 0 + 12 + 0 + 8
    接下来把这些乘积的每一位数字相加：
    2 + 0 + 0 + 0 + 0 + 1 + 2 + 0 + 8 = 13
2. 把上述结果（13）加上未乘以2的各位数字的和（从末尾开始数）：
    13 + 4 + 0 + 0 + 0 + 0 + 0 + 3 + 0 = 20
3. 最终总和（20）的最后一位是0，因此大卫的卡号格式合法。
由此可见，校验信用卡号的逻辑并不复杂，但手动计算会比较繁琐，我们来把它写成程序吧。

## 实现细节
在`credit`文件夹的`credit.c`文件中编写程序，提示用户输入信用卡号，然后根据前文提到的各卡组织格式规则，通过`printf`输出该卡号属于合法的美国运通卡、万事达卡、维萨卡，或是无效卡号。为了便于自动化测试，要求程序的最后一行输出必须为`AMEX\n`、`MASTERCARD\n`、`VISA\n`或`INVALID\n`，不允许多输出或少输出任何内容。
为简化实现，你可以假设用户输入将全为数字（即不含实体卡面上可能印有的连字符），且不包含**前导零（leading zeroes）**。但不要假设用户输入可以存入`int`类型变量！最好使用CS50库提供的`get_long`函数获取用户输入。（想想这是为什么？）
以下是输入有效信用卡号（不含连字符）时的程序运行效果示例：
```
$ ./credit
Number: 4003600000000014
VISA
```
`get_long`本身会自动拒绝连字符（以及其他非数字输入）：
```
$ ./credit
Number: 4003-6000-0000-0014
Number: foo
Number: 4003600000000014
VISA
```
但你需要自行识别不属于信用卡号的输入（比如电话号码），即便输入全为数字：
```
$ ./credit
Number: 6176292929
INVALID
```
请用大量不同的输入测试你的程序，包括合法和非法的场景（我们评分时肯定会这么做！）。你可以参考PayPal官方提供的[测试卡号列表](https://developer.paypal.com/api/nvp-soap/payflow/integration-guide/test-transactions/#standard-test-cards)。
如果你的程序在某些输入下表现异常（甚至无法编译），就该开始调试了！

【难句解析】
1. 原文：That checksum enables computers (or humans who like math) to detect typos (e.g., transpositions), if not fraudulent numbers, without having to query a database, which can be slow.
   译文：这种校验和机制让计算机（或是喜欢数学的人）无需查询数据库（查询操作速度较慢）就能检测出输入错误（比如数字换位），甚至可以识别部分伪造卡号。
   解析：本句包含多层插入语和非限定性定语从句，翻译时调整语序，将修饰`database`的定语从句提前补充说明查询的特性，符合中文叙事逻辑；将易产生歧义的`if not fraudulent numbers`意译为“甚至可以识别部分伪造卡号”，准确传达原文的递进含义：卢恩算法可排查输入错误，也能过滤不符合规则的假卡号，但无法完全识别所有伪造卡号。
2. 原文：Multiply every other digit by 2, starting with the number’s second-to-last digit, and then add those products’ digits together.
   译文：从卡号的倒数第二位开始，每隔一位取出数字乘以2，再将所有乘积的每一位数字相加（而非直接相加乘积本身）。
   解析：本句是卢恩算法的核心规则，翻译时特意补充括号内的说明，避免学习者误解为直接相加乘积的总和；调整了方式状语的语序，先说明操作起始位置，再说明操作步骤，符合中文技术指令“先前提、后动作”的表达习惯，确保核心规则传递无偏差。
3. 原文：For simplicity, you may assume that the user’s input will be entirely numeric (i.e., devoid of hyphens, as might be printed on an actual card) and that it won’t have leading zeroes.    译文：为简化实现，你可以假设用户输入将全为数字（即不含实体卡面上可能印有的连字符），且不包含前导零。但不要假设用户输入可以存入`int`类型变量！最好使用CS50库提供的`get_long`函数获取用户输入。（想想这是为什么？）
   解析：本句包含多个实现前提和注意事项，翻译时明确区分“可假设”和“不可假设”的边界，补充“变量”二字让`fit in an int`的含义更清晰，符合C语言入门学习者的认知；最后的反问句保留原文的引导语气，鼓励学习者思考数据类型选择的原因（16位信用卡号远超32位`int`的最大存储范围2^31-1=2147483647）。
